## 1. 上下文管理问题

### 1.1 上下文窗口限制

**问题描述**：
- 大型项目代码量远超模型上下文窗口
- 重要上下文被截断导致生成代码不完整
- 会话过长后模型"遗忘"早期指令

**典型场景**：
```
项目代码: 50万行
模型窗口: 200K tokens (约 15万行)
结果: 只能看到 30% 的代码
```

**影响**：
- 生成的代码缺少必要的 import
- 调用不存在的函数或方法
- 类型定义不匹配
- 重复造轮子（不知道已有实现）

### 1.2 上下文污染

**问题描述**：
- 无关代码占用宝贵的上下文空间
- 错误的示例代码误导模型
- 多次迭代后累积的"垃圾"上下文

**典型场景**：
```
用户: 修复这个 bug
AI: [生成修复代码]
用户: 不对，试试另一种方法
AI: [生成新代码，但仍受前一次错误尝试影响]
```

### 1.3 跨文件理解困难

**问题描述**：
- 模型难以理解分散在多个文件的业务逻辑
- 模块间依赖关系不清晰
- 配置文件与代码的关联性丢失

## 2. 代码质量问题

### 2.1 过度工程化

**问题描述**：
- AI 倾向于生成"完整"但过于复杂的解决方案
- 添加不必要的抽象层
- 引入用不到的设计模式

**典型表现**：
```typescript
// 用户需求: 一个简单的配置读取
// AI 生成: 完整的配置管理系统
class ConfigManager {
  private static instance: ConfigManager;
  private config: Map<string, any>;
  private observers: Observer[];
  private validators: Validator[];
  // ... 200 行代码
}

// 实际只需要:
const config = JSON.parse(fs.readFileSync('config.json'));
```

### 2.2 代码风格不一致

**问题描述**：
- 生成代码与项目现有风格不匹配
- 命名规范不统一（camelCase vs snake_case）
- 注释风格混乱

**典型表现**：
```typescript
// 项目现有风格
function getUserById(id: string) { }

// AI 生成
function get_user_by_id(userId: string) { }  // 命名风格不一致
```

### 2.3 幻觉问题（Hallucination）

**问题描述**：
- 调用不存在的 API
- 编造库的方法或属性
- 虚构的配置选项

**典型表现**：
```typescript
// AI 生成的代码
import { useAutoComplete } from 'react';  // 不存在的 Hook

// 使用过时的 API
componentWillMount() {  // React 17+ 已废弃
  this.fetchData();
}
```

### 2.4 安全漏洞

**问题描述**：
- SQL 注入风险
- XSS 漏洞
- 敏感信息硬编码
- 不安全的依赖版本

**典型表现**：
```typescript
// AI 生成的危险代码
const query = `SELECT * FROM users WHERE id = ${userId}`;  // SQL 注入

// 正确写法
const query = 'SELECT * FROM users WHERE id = ?';
db.query(query, [userId]);
```

## 3. Prompt 工程挑战

### 3.1 需求表达不清

**问题描述**：
- 自然语言的歧义性
- 隐含需求未被识别
- 边界条件未说明

**对比示例**：
```
模糊的 Prompt:
"帮我写一个登录功能"

清晰的 Prompt:
"实现用户登录功能，要求：
- 支持邮箱/手机号两种方式
- 密码需 BCrypt 加密
- 失败 5 次锁定 30 分钟
- 返回 JWT Token，有效期 7 天
- 集成现有的 UserService"
```

### 3.2 上下文信息不足

**问题描述**：
- 未提供项目技术栈信息
- 未说明依赖版本
- 缺少业务背景

**影响**：
- 生成代码使用错误的框架版本 API
- 与项目架构不兼容
- 业务逻辑错误

### 3.3 迭代沟通成本

**问题描述**：
- 需要多轮对话才能得到满意结果
- 修正一个问题引入新问题
- 难以精确描述"哪里不对"

## 4. 多模型协作问题

### 4.1 输出格式不统一

**问题描述**：
- 不同模型的 Diff 格式不同
- 代码块语法不一致
- 响应结构难以解析

**典型表现**：
```diff
# Codex 输出
--- a/src/utils.ts
+++ b/src/utils.ts
@@ -10,3 +10,5 @@
+ new line

# Gemini 输出
```typescript
// Modified src/utils.ts
new line
```

### 4.2 方案冲突

**问题描述**：
- 不同模型给出矛盾的建议
- 技术选型意见分歧
- 难以判断哪个方案更优

**典型场景**：
```
Codex: 建议使用 Redux 管理状态
Gemini: 建议使用 Zustand 更轻量
Claude: 建议用 React Context 足够

用户: ???
```

### 4.3 交叉验证困难

**问题描述**：
- 模型 A 无法有效审查模型 B 的代码
- 都倾向于认可对方的方案
- 难以发现共同的盲点

## 6. 安全与合规问题

### 6.1 代码泄露风险

**问题描述**：
- 代码发送到外部 API
- 敏感信息可能被记录
- 合规要求限制使用

**风险场景**：
```
项目包含:
- API 密钥
- 数据库凭证
- 客户数据处理逻辑
- 专有算法

发送给 AI 后:
- 可能被用于模型训练
- 可能被日志记录
- 违反数据保护法规
```

### 6.2 许可证问题

**问题描述**：
- AI 生成代码的版权归属不明
- 可能包含受版权保护的代码片段
- 开源许可证合规风险

### 6.3 审计追踪

**问题描述**：
- 难以追踪 AI 生成的代码
- 代码审查责任不清
- 出问题时难以定位原因

## 7. 用户常犯错误与反模式

> 这些是在 AI Coding 实践中观察到的常见错误行为，识别并避免这些模式可以显著提升效率。

### 7.1 重复提问综合症

**问题描述**：
- 同一个问题反复问，每次都得到相似的错误答案
- 期望 AI "这次会不一样"，但不改变提问方式
- 不断刷新对话，从头开始问同样的问题

**典型表现**：
```
第 1 次: "为什么这个代码报错？"
AI: [给出解决方案 A]
用户: 不行

第 2 次: "为什么这个代码报错？"
AI: [给出几乎相同的解决方案 A']
用户: 还是不行

第 3 次: "为什么这个代码报错？？？"
AI: [继续给出类似方案...]
```

**根本原因**：
- 没有提供新的信息（错误日志、尝试结果）
- 期望 AI 自动猜到问题所在
- 不理解 AI 是基于输入生成输出

**正确做法**：
```
"这个代码报错，我已经尝试了方案 A（具体描述），
但出现了新错误：[错误信息]。
环境是 Node 18 + TypeScript 5.3。
还有什么其他可能的原因？"
```

---

### 7.2 模糊反馈循环

**问题描述**：
- 只说"不对"、"不行"、"有问题"，不说具体哪里不对
- AI 无法定位问题，只能盲目猜测
- 陷入无效的来回沟通

**典型表现**：
```
用户: 帮我写一个排序函数
AI: [生成快速排序代码]
用户: 不对
AI: [生成归并排序代码]
用户: 还是不对
AI: [生成冒泡排序代码]
用户: 你到底会不会？
```

**问题分析**：
- 用户可能想要的是"按特定字段排序"
- 或者是"稳定排序"
- 或者是"降序排序"
- AI 无从得知具体需求

**正确做法**：
```
"不对，我需要的是：
1. 按对象的 createdAt 字段排序
2. 降序（最新的在前）
3. 相同时间的保持原有顺序（稳定排序）"
```

---

### 7.3 情绪化与攻击性沟通

**问题描述**：
- 用情绪化语言发泄不满，而非描述问题
- 攻击性表达不会让 AI 变"聪明"
- 浪费时间在无效沟通上

**典型表现**：
```
用户: 你怎么这么笨？我说了不要用 any！
用户: 你是不是蠢？这都不会？
用户: 废物，又错了
用户: 我都说了多少遍了！！！
用户: 你到底行不行啊？？？
```

**为什么无效**：
- AI 不会因为被骂而"更努力"
- 情绪化语言不包含有用信息
- 模型无法从"蠢"中推断出正确方案
- 这些时间本可用于清晰描述需求

**问题根源**：
```
用户期望: AI 应该"理解"我的意图
实际情况: AI 只能处理明确的输入信息

用户想表达: 不要用 any 类型
实际说了: "你怎么这么笨"
AI 收到的有用信息: 0
```

**正确做法**：
```
错误方式:
"你怎么这么笨？我说了不要用 any！"

正确方式:
"请修改以下代码，将所有 any 类型替换为具体类型：
- line 15: data: any → data: UserData
- line 23: response: any → response: ApiResponse<User>
项目中的类型定义在 src/types/ 目录下"
```

**对比效果**：
| 表达方式 | AI 可提取的信息 | 预期效果 |
|---------|----------------|---------|
| "你是不是蠢" | 无 | 无改善 |
| "又错了" | 有错误 | 不知道错在哪 |
| "不要用 any" | 避免 any | 可能有改善 |
| "把 line 15 的 any 改成 UserData" | 精确位置+目标类型 | 直接解决 |

**心态调整**：
- AI 是工具，不是员工，不会因批评而改进
- 每次"骂"AI 的时间，不如用来写清楚需求
- 清晰的 Prompt 比情绪化表达效率高 10 倍

---

### 7.4 不读输出直接否定

**问题描述**：
- AI 生成了正确的代码，但用户没仔细看就说不行
- 复制代码时漏了一部分
- 没有按照 AI 的说明进行配置

**典型表现**：
```
AI: 请先安装依赖: npm install lodash
    然后使用以下代码: [代码]

用户: [直接复制代码，不装依赖]
用户: 报错了！你的代码有问题！

实际错误: Cannot find module 'lodash'
```

**正确做法**：
- 完整阅读 AI 的回复
- 按步骤执行所有前置条件
- 报错时先检查是否遗漏了什么

---

### 7.5 过度依赖 AI 判断

**问题描述**：
- 让 AI 做它不擅长的判断（业务决策、产品需求）
- 把 AI 当作全知的权威
- 不验证 AI 的输出就直接使用

**典型表现**：
```
用户: 我应该用 React 还是 Vue？
AI: 建议使用 React，因为...

用户: [直接选择 React，不考虑团队技术栈]
后果: 团队没人会 React，项目延期
```

**正确做法**：
- AI 适合执行，人类负责决策
- 让 AI 列出选项的利弊，自己做最终决定
- 结合团队实际情况判断

---

### 7.6 一次性巨型请求

**问题描述**：
- 把所有需求塞进一个超长的 Prompt
- 期望 AI 一次性完成整个系统
- 需求之间相互矛盾或不清晰

**典型表现**：
```
用户: 帮我写一个电商系统，要有用户管理、商品管理、
订单管理、支付系统、物流追踪、数据分析、推荐系统、
客服系统、营销工具、库存管理......

AI: [生成一个庞大但质量低下的代码框架]
```

**问题分析**：
- 上下文过载，每个模块都做不好
- 模块间关系混乱
- 无法迭代优化

**正确做法**：
```
Step 1: "设计用户管理模块的数据模型"
Step 2: "实现用户注册和登录 API"
Step 3: "添加 JWT 认证中间件"
...
逐步构建，每步验证
```

### 7.7 忽略错误信息

**问题描述**：
- 有详细的错误堆栈，但不提供给 AI
- 只说"报错了"，不说什么错
- 截图而非复制文本（AI 无法搜索/分析）

**典型表现**：
```
用户: 代码跑不起来，帮我看看
AI: 请提供错误信息
用户: 就是报错了
AI: 请提供具体的错误信息
用户: [发了一张模糊的截图]
```

**正确做法**：
```
"运行时出现以下错误：

TypeError: Cannot read property 'map' of undefined
    at UserList.render (UserList.tsx:23)
    at processChild (react-dom.js:1234)

相关代码在 UserList.tsx 第 23 行：
{users.map(user => <UserItem key={user.id} />)}
"
```

### 7.8 不断切换话题

**问题描述**：
- 一个问题没解决完就跳到下一个
- 同一会话混杂多个不相关的任务
- 上下文混乱导致 AI 困惑

**典型表现**：
```
用户: 帮我修复登录 bug
AI: [开始分析登录代码]
用户: 对了，顺便帮我加个暗黑模式
AI: [切换到样式代码]
用户: 登录那个改好了吗？
AI: [上下文已混乱]
```

**正确做法**：
- 一个会话专注一个任务
- 任务完成后再开始新任务
- 复杂任务使用 TodoWrite 跟踪

### 7.9 不看文档直接问

**问题描述**：
- 官方文档有清晰说明，但不查就问 AI
- AI 的知识可能过时，文档才是权威
- 浪费时间在 AI 可能给出错误答案的问题上

**典型表现**：
```
用户: React 19 的 use() hook 怎么用？

AI: [基于训练数据给出可能过时的答案]

实际情况: React 19 的 API 可能已经变化，
应该查看官方文档获取最新用法
```

**正确做法**：
```
1. 先查官方文档
2. 文档看不懂再问 AI 解释
3. 或者使用 Context7 MCP 获取最新文档

mcp__context7__query-docs
"React 19 use hook usage"
```

### 7.10 修改后不测试

**问题描述**：
- AI 生成代码后直接合并，不运行测试
- 假设 AI 生成的代码一定正确
- 问题累积到后期才发现

**典型表现**：
```
Day 1: AI 生成模块 A（有隐藏 bug）
Day 2: AI 生成模块 B（依赖 A 的错误行为）
Day 3: AI 生成模块 C（进一步放大问题）
Day 4: 集成测试，全面崩溃
```

**正确做法**：
```bash
# 每次修改后立即验证
pnpm type-check  # 类型检查
pnpm lint        # 代码规范
pnpm test        # 单元测试

# 确保通过后再继续下一步
```

### 7.11 拒绝学习基础

**问题描述**：
- 完全依赖 AI 写代码，不理解代码原理
- 遇到问题无法自己调试
- 长期下来技术能力退化

**典型表现**：
```
用户: 帮我写 XX
用户: 帮我改 YY
用户: 为什么报错？帮我修
用户: 这个代码是干嘛的？（自己之前让 AI 写的）
```

**正确做法**：
- AI 是工具，不是替代品
- 要求 AI 解释代码原理
- 定期自己手写代码保持能力
- 使用 AI 学习，而非逃避学习

## 8. 最佳实践与解决方案

### 8.1 上下文管理策略

**精准上下文注入**：
```markdown
使用 Auggie MCP 进行语义检索，而非全量导入

推荐:
mcp__auggie-mcp__codebase-retrieval
"Where is user authentication implemented?"

避免:
@src/**/*.ts (全量导入)
```

**会话管理**：
- 复杂任务拆分为多个短会话
- 定期总结并重新开始
- 使用 CLAUDE.md 持久化项目约定

### 8.2 代码质量保障

**强制约束**：
```markdown
在 Prompt 中明确：
1. "遵循项目现有代码风格"
2. "最小化改动，不要过度工程化"
3. "只修改需求相关的代码"
```

**自动审查**：
```bash
# 每次生成后强制执行
pnpm type-check
pnpm lint
pnpm test
```

### 8.3 Prompt 工程技巧

**结构化 Prompt 模板**：
```markdown
## 任务
[一句话描述]

## 上下文
- 技术栈: [框架/版本]
- 相关文件: [路径列表]
- 约束条件: [限制]

## 期望输出
- 格式: [Unified Diff / 完整代码]
- 范围: [仅修改哪些文件]

## 反例
[不要做什么]
```

### 8.4 多模型协作流程

**职责分离**：
```
Phase 1: Claude 收集上下文
Phase 2: Codex + Gemini 并行分析
Phase 3: Claude 整合方案，人工确认
Phase 4: Claude 实施
Phase 5: Codex + Gemini 交叉审计
```

**冲突解决**：
- 技术选型冲突 → 列出利弊，人工决策
- 实现细节冲突 → 以项目现有风格为准
- 都不确定 → 写 PoC 验证

### 8.5 安全实践

**敏感信息隔离**：

项目结构:
├── .env              # 不发送给 AI
├── .env.example      # 可以发送
├── secrets/          # 整个目录排除
└── src/              # 正常处理
```

```

## 常见问题速查表

| 问题 | 快速解决方案 |
|------|-------------|
| 代码不完整 | 检查上下文是否包含相关依赖文件 |
| 风格不一致 | 在 Prompt 中引用现有代码示例 |
| 幻觉 API | 使用 Context7 MCP 获取最新文档 |
| 生成过慢 | 缩小上下文范围，精准检索 |
| 方案冲突 | 明确决策标准（性能/可维护性/时间） |
| 安全顾虑 | 使用本地模型或企业版 |

## 总结

AI Coding 的核心挑战可归结为：

1. **上下文** - 如何让 AI 理解足够多的信息
2. **质量** - 如何保证生成代码符合标准
3. **协作** - 如何有效地人机/机机协作
4. **安全** - 如何在效率和安全间平衡

解决这些问题的关键是：
- 建立明确的工作流程
- 制定清晰的 Prompt 规范
- 实施自动化质量检查
- 保持人工审查的最终决定权
